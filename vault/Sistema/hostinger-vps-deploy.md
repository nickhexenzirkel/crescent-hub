O **crescent-hub-server** (ver [[alexa-token-persistencia]], [[unikowave-architecture]]) **não está mais no Render** — migrado (jul/2026) pra uma VPS da Hostinger, processo gerenciado por **PM2** (nome do processo: `crescent-hub-server`).

**Acesso SSH:** `ssh root@187.127.27.98` (usuário `root`, criado direto na hPanel). O IP de VPS Hostinger normalmente é fixo; se não conectar, conferir em hPanel → VPS → Visão Geral → IPv4.

**Deploy de mudanças no servidor:**
```
ssh root@187.127.27.98
cd <pasta-do-crescent-hub-server>
git pull
pm2 restart crescent-hub-server
```

**Como ver logs:**
- Via SSH: `pm2 logs crescent-hub-server` (ao vivo) ou `pm2 logs crescent-hub-server --err --lines 100 --nostream` (só erros, sem ficar tailando). Arquivos brutos em `~/.pm2/logs/`.
- Via UI (jul/2026): aba **"Logs do Servidor"** no Dashboard RH (`crescent-hub/src/modules/dashboard-rh/index.jsx`), consome `GET /api/logs` (admin-only, definido em `crescent-hub-server/index.js`) — acha o processo PM2 certo (por `pm_id` do próprio processo, fallback pelo nome), lê só o final (tail) dos arquivos de log do PM2 e devolve status/uptime/memória/CPU + linhas de erro/saída. Tela mostra cards de status, filtro Erros/Saída e console com auto-refresh de 5s.

**Causa do bug que motivou essa feature:** `/api/status` (endpoint que a Central Alexa usa pra saber se o Spotify tá conectado) engolia o erro num `catch {}` sem logar nada — então mesmo tendo acesso aos logs não dava pra saber POR QUE tava "Spotify desconectado". Corrigido junto: agora loga o erro real (`console.error`) e devolve `reason` no JSON de resposta.

**Pendência a reavaliar:** as mitigações de RAM feitas pro plano free do Render (análise de ritmo serializada, Chromium com flags low-mem, fallback Playwright/Chromium desligado — ver [[unikowave-architecture]]) foram pensadas pro limite de 512MB de lá. Numa VPS Hostinger isso pode não ser mais o gargalo — vale medir a RAM disponível e considerar reativar o fallback Playwright se sobrar memória.

**Rate limit diário do Spotify — 2ª causa confirmada (2026-07-14):** rate limits de retry-after GIGANTE (visto `22210s` ≈ 6h) voltaram, mas o Render estava FORA (curl `crescent-hub-server.onrender.com/api/status` → 503 imediato), então NÃO era a instância paralela dessa vez. A causa foi **volume constante de chamadas ao Spotify estourando a cota diária do app**: `monitorPlayback` batia em `/me/player/currently-playing` a cada **4s, 24h/dia, mesmo ocioso** (~21 mil chamadas/dia só disso) + `/api/status` chamando `/me` a cada poll de cada máquina com a Central aberta. **Fix (commit no crescent-hub-server):** monitor com cadência adaptativa (4s tocando / 20s ocioso, loop auto-agendado que retorna se está tocando), `/api/status` com cache de 30s (pos+neg), `/api/progress` TTL 1.5s→5s (serve o cache do monitor), e teto de 20min no retry-after honrado do 429 (evita ficar 6h fora). Se voltar a acontecer: (1) reduzir mais a cadência ociosa, (2) checar se o app Spotify está em Development Mode (cota baixa) e pedir Extended Quota Mode no dashboard do Spotify.

**CONFIRMADO (2026-07-14): o app ESTÁ em Development Mode** — esse é o teto estrutural do 429. Fatos da política atual do Spotify: rate limit é por janela deslizante de 30s, e o teto do dev mode é MUITO menor que o do Extended Quota. Desde **11/fev/2026** o Spotify apertou o dev mode (exige conta Premium + só 5 usuários de teste). Extended Quota Mode só é concedido a **organizações** (e-mail corporativo + formulário), via link "Request Extension" na página do app no Developer Dashboard — pessoa física não pode mais pedir (regra de 15/mai/2025). Como é ferramenta interna da empresa, dá pra pedir como org. Enquanto não aprovam: sobreviver dentro do teto = nunca ter rajada (cadência adaptativa do monitor + caches já ajudam; paliativo extra = monitor ocioso 20s→40s, cache /api/status 30s→60s). No frontend (crescent-hub) já cortei busca de 1 char + debounce 450→650ms em [[central-alexa]] handleSearch/handleReplaceSearch.

**Ban de COTA DIÁRIA vs rate limit transitório (2026-07-14):** depois de aplicar as reduções, apareceu `retry-after real 61707s` (≈17h) — isso NÃO é o rate limit de rajada (janela de 30s, volta em segundos/min), é a **cota diária do app zerada** (característico do Development Mode). Nenhum deploy/restart levanta um ban ativo — só espera o reset (o timer conta pra baixo sozinho). O wrapper `spotify()` em `crescent-hub-server/index.js` (~linha 1233) tem guard global `rateLimitedUntil`; antes capava tudo em 1200s e sondava a cada 20min. Fix: passou a distinguir `isDailyBan = raRaw > 1200` → re-checa a cada 1h (não 20min) e loga "⛔ BAN DE COTA DIÁRIA". Servidor: monitor ocioso 20s→40s, cache /api/status 30s→60s, cache de busca 60s→180s + chave normalizada (colapsa espaços). **Nota de bug conhecido:** o guard `rateLimitedUntil` tem brecha de thundering-herd — chamadas concorrentes no mesmo instante passam todas antes do guard ser setado (por isso aparecem 2 "pausando" seguidos). **Ainda a descartar:** ban de 17h com só 18 usuários é anormal → checar `pm2 list` na VPS por PROCESSO DUPLICADO do crescent-hub-server (mesma lógica do bug do Render paralelo). Se duplicado, matar o extra. **CHECADO (2026-07-14): `pm2 list` mostra 1 processo só, SEM duplicata na VPS.** Render suspenso. Então o ban de 17h é provavelmente CASTIGO ESCALADO pelo Spotify — o comportamento antigo (thundering-herd + sondar a cada 20min insistindo durante o 429) fazia a punição subir de min→horas; código novo não deve mais cavar esse buraco. Faltou descartar: cópia LOCAL do server rodando `node index.js` com as mesmas credenciais Spotify (há clones em Downloads/backup*, Videos/crescent-hub-server). **Próximo passo se reincidir com código novo no ar:** throttle GLOBAL de verdade no wrapper `spotify()` (fila com teto de N chamadas/30s), em vez de só reagir ao 429 depois de estourar.

**BUG CRÍTICO encontrado (2026-07-09): o serviço antigo no Render ficou rodando em paralelo com a VPS.** Confirmado pelo usuário que o Render (`crescent-hub-server.onrender.com`) ainda estava ativo dias depois da migração. As duas instâncias compartilham o MESMO Client ID Spotify e o MESMO registro Alexa (guardados no Supabase `settings`), então ficam brigando pela renovação do refresh token — cada uma invalida o token que a outra acabou de renovar. Sintomas observados nos logs da VPS: `⏸ Rate limit Spotify — pausando chamadas por 24636s` (~6h51, retry-after de HORAS é anormal — Spotify normalmente pune em segundos/minutos, isso indica volume de chamadas em dobro no mesmo app), `invalid_grant`/`Invalid authorization code` repetido no `/callback`, e `Alexa: registration data expirada` reaparecendo mesmo com o fix de auto-renovação. **Ação pedida ao usuário: suspender/deletar o serviço no Render.** Se o "Spotify desconectado" ou os rate-limits gigantes voltarem a aparecer, a PRIMEIRA coisa a checar é se por acaso o Render foi reativado (redeploy automático, etc.) — não assumir que é outro bug antes de descartar isso.
